文献综述智能体 MVP：宿主实现路径

目标约束：工作台型 B/S、检索+筛选型、国外优先、编排型 Agent、尽量复用现成开源、院内/私有化优先

推荐

A. Dify 作为 B/S 宿主

把 Dify 当成前台工作台和编排入口，检索、去重、筛选、PRISMA 作为外部工具服务接入。

优点

  • 现成 B/S 产品完成度高
  • 多应用、多工作流、多角色易搭建
  • 最适合先做可演示 MVP

限制

  • 不是医学科研专用工作台
  • 题录筛选和人工复核界面需要外挂
  • 复杂状态流不如专门业务前端自然

B. Flowise / Langflow 作为编排宿主

更偏可视化流程编排，适合把工具链快速串起来，但产品化工作台能力弱于 Dify。

优点

  • 流程节点化直观
  • 二次接工具方便
  • 便于验证 agent 编排逻辑

限制

  • 业务工作台感偏弱
  • 人机协同审阅体验一般
  • 最终往往还要补一层前端

C. 自建轻量工作台，外接专业组件

自己做一个很薄的任务工作台，ASReview/AiReview/GROBID 等作为后端服务接入，最贴业务，但代码量上升。

优点

  • 最贴合筛选与复核流程
  • 后续扩展全文抽取更顺
  • 院内私有化控制最好

限制

  • 不是最小开发量
  • 第一版交付周期更长
  • 需要自己维护任务状态与 UI

我的建议

推荐路径：A. Dify 作为 B/S 宿主

原因不是它最专业，而是它最符合当前约束：最小代码量、现成 B/S、方便做编排型 Agent、适合快速拼接外部工具服务并先把闭环跑通。

边界要讲清楚：Dify 只做宿主与编排，不负责医学文献筛选、专业审阅和 PRISMA 这些能力本身，这些仍由外部开源组件承担。
